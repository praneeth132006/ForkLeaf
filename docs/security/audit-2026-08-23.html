01

Executive summary

ForkLeaf is a genuinely well-secured application. It treats the GitHub access token as the single asset worth protecting and builds the whole architecture around never letting it reach the browser — and the defenses that follow from that decision are consistent, layered, and correct.

The assessment covered the three surfaces the app actually presents: the browser-facing web application, its /api/gh/* GitHub proxy, and its Firebase/Firestore backend. Every offensive technique in scope was probed against both the source and the live deployment. No critical or high-severity vulnerabilities were confirmed. The findings that remain are one architectural blast-radius concern and a handful of hardening and hygiene items.

02

Scope & authorization

Testing was authorized by the application owner against assets they control: the deployed instance at forkleaf.vercel.app and the full source tree in this repository. All live probing was read-only and non-destructive — unauthenticated endpoint checks, header inspection, an origin-rejection probe, and an OAuth-start inspection. No accounts were created, no repositories were written, no real data was exfiltrated, and no denial-of-service load was generated.

What "in and out" means here

In — a static read of the server code: session and token handling, the GitHub proxy, the markdown/Mermaid render pipeline, and the Firestore rules. Out — live behavioural probes of the running deployment to confirm the code's guarantees actually ship.

03

Findings

Each finding carries the offensive technique that would exercise it (red) and the paired defensive control that detects or prevents it (blue), following the RedBlueSkills discipline that every offensive result must name its counterpart.

M-01

OAuth grant is repository-wide (repo scope)

Medium

Sign-in requests the classic repo scope, confirmed live on the authorize redirect (scope=repo+read:user). That grant gives ForkLeaf read/write access to every repository the user can reach, public and private — far more than the notes repository the product actually uses. The code documents this as a deliberate trade-off (there is no narrower classic scope that still writes to private repos), but it defines the blast radius of any token compromise: whoever holds a decrypted session can touch all of a user's code, not just their notes.

Endpoint

/api/auth/github → GitHub authorize

Red

api-broken-authentication — token scope abuse widens the reachable surface once a session is captured.

Blue

api-authentication-monitoring, ci-identity-access-hardening

Fix

Offer (or default to) a GitHub App with fine-grained, per-repository permissions so the grant matches the one notes repo. Where the classic OAuth path stays, keep documenting the trade-off prominently, as the code already does.

M-02

Stateless 30-day session cannot be revoked

Medium

The session is a self-contained JWE (A256GCM) valid for 30 days. There is no server-side session store, so /api/auth/logout only deletes the browser's copy of the cookie — a cookie already captured by an attacker stays valid until it expires. The only way to invalidate every outstanding session is to rotate SESSION_SECRET, which signs everyone out at once. Combined with M-01's broad grant, a leaked cookie is both powerful and long-lived.

Endpoint

lib/session.ts, /api/auth/logout

Red

web-broken-authentication — session token replay after theft; no revocation to shorten the window.

Blue

web-authentication-hardening

Fix

Shorten the lifetime (or add a sliding refresh), and record a per-session jti so a single session can be revoked without a global secret rotation. A durable store (Upstash/Redis) is the natural home once one is added for M-03.

L-01

Read API routes are unthrottled

Low

Write routes (commit, asset, publish, fork, pull, bootstrap) all call enforceRateLimit. The read routes — repos, tree, file, history, branches, and the raw image proxy — do not. A runaway or hostile authenticated client can burn the user's GitHub API quota, and raw can be driven as an authenticated image-fetch proxy.

Endpoint

/api/gh/{repos,tree,file,history,branches,raw}

Red

api-unrestricted-resource-consumption

Blue

api-rate-limit-hardening

Fix

Apply the existing enforceRateLimit to the read routes with a generous per-minute budget; they already have the helper on hand.

L-02

Rate limiter is in-memory and per-instance

Low

The limiter keeps its counters in a module-level Map. On Vercel's serverless/Fluid runtime each instance has its own copy, so the effective limit scales with instance count and resets on cold start. The code is candid about this ("a brake rather than a guarantee"), so this is confirmation rather than surprise: it stops accidental retry loops but not a distributed attacker.

Endpoint

lib/rate-limit.ts

Red

api-unrestricted-resource-consumption (distributed)

Blue

api-rate-limit-hardening

Fix

Move to a durable limiter (Upstash Redis) when a real ceiling is needed. The call sites are already shaped to swap the backend without change.

L-03

CSP img-src https: allows any-host image beacons

Low

To let notes embed images from anywhere, the policy sets img-src 'self' data: blob: https:. A note opened from an untrusted repository can therefore reference an image on an attacker's host, and simply viewing the note leaks the reader's IP, user-agent, and the fact of the view to that host. No script executes — img-src can't — so this is a privacy/tracking leak, not code execution. It is a reasonable UX trade-off, worth stating so it's a known one.

Endpoint

proxy.ts → Content-Security-Policy

Red

web-http-fingerprinting / passive tracking via remote assets

Blue

web-security-headers

Fix

Optional: proxy remote images through /api/gh/raw-style same-origin fetch, or offer a "block remote images" reading mode. Low priority given the local-first threat model.

I-01

Firebase profile identity is client-asserted

Info

The Firestore profile is written by the client under an anonymous Firebase UID, and githubId/githubLogin are supplied by that client. The rules validate field types but not that the GitHub identity truly belongs to the caller. This has no security impact: the document is owner-read-only, display-only, and is never consulted for authorization — the server session cookie is. The rules file states this explicitly. Noted for completeness.

firestore.rules, lib/firebase/users.ts

Info

04

Tested & clean

The following techniques were exercised and the corresponding defense held. These are the load-bearing controls — worth knowing what protects you, not just what doesn't.

  • ✓

    Stored XSS in the note preview. Markdown is rendered with rehype-sanitize, allowDangerousHtml off, an explicit tag/attribute allowlist, and data: URLs constrained to raster images. Raw HTML in notes is escaped.

  • ✓

    XSS via Mermaid diagrams. Mermaid runs at securityLevel:"strict" with htmlLabels:false, and every SVG is re-sanitised with DOMPurify — foreignObject, script, and event-handler attributes forbidden.

  • ✓

    SSRF & path traversal into the GitHub API. A single transport choke-point rejects off-host URLs and any ../. segment (decoded, so %2e%2e can't slip past); paths are per-segment encoded and names/refs validated by strict regex.

  • ✓

    Cross-site request forgery. Confirmed live: a state-changing POST with a foreign Origin is refused with 403. Backed by a SameSite=Lax cookie and an origin allowlist in middleware.

  • ✓

    Login CSRF. Single-use OAuth state, constant-time compared, in a Secure; HttpOnly; SameSite=Lax 10-minute cookie — verified on the live authorize redirect.

  • ✓

    Access-token exposure. The token never reaches the browser: encrypted (JWE A256GCM) into an httpOnly cookie, with a hard startup failure if SESSION_SECRET is missing or under 32 chars — no insecure fallback.

  • ✓

    Publish path traversal. pagePath validates the slug against an allowlist before use — not after normalising — so ../index is rejected rather than quietly rewritten.

  • ✓

    IDOR / broken object-level access. Not applicable by design: every repository operation is delegated to the signed-in user's own GitHub token, so GitHub itself enforces per-object authorization. There is no ForkLeaf-side object store to walk.

  • ✓

    Firestore rules. Default-deny catch-all, owner-only read/write on users/{uid}, a strict field allowlist, and delete:false. New collections must opt in.

  • ✓

    Security headers. Confirmed live: full CSP with a per-request nonce + strict-dynamic on the content-rendering routes, HSTS (2y, preload), X-Frame-Options: DENY, nosniff, COOP, CORP, Referrer-Policy, and a locked-down Permissions-Policy.

07

Prioritized remediation

  1. Add rate limiting to the read routes (L-01).Highest impact-per-effort: the helper exists; wire enforceRateLimit into tree, file, history, repos, branches, and raw. An afternoon.
  2. Make sessions revocable (M-02).Add a per-session jti and shorten the lifetime or add sliding refresh, so a stolen cookie has a bounded, closable window.
  3. Offer a fine-grained GitHub App path (M-01).Narrow the default grant to the notes repository; the largest reduction in blast radius, though the most product work.
  4. Introduce a durable rate limiter (L-02).Upstash Redis behind the existing interface; naturally also hosts the session jti denylist from step 2.
  5. Decide on remote-image policy (L-03).Keep as-is with the trade-off documented, or add a "block remote images" reading mode. Low urgency.
